# Как найти и сопрячь Mi Band 1A (и почему не получается)

## Почему браслет «не находится»

Mi Band 1A — не маячок с постоянной рекламой. Она включает advertising
только в некоторых состояниях:

- после нажатия кнопки/встряхивания;
- после зарядки;
- после сброса;
- когда порвано соединение с телефоном.

Если Mi Fit/Zepp/телефон держит соединение, браслет для ESP32 **невидим**:
BLE-централь может быть только одна.

Отсюда типичные ошибки:

```
RuntimeError: браслет не найден в эфире
MIBAND: auto poll: таймаут, браслет не найден
```

Это не «код сломался» и не «браслет умер»: устройство не рекламируется.

## Правильный порядок

1. **Освободить браслет от телефона**: выключить Bluetooth на телефоне
   или закрыть Mi Fit/Zepp. Не удаляй сопряжение в телефоне без нужды.
2. **Разбудить браслет**: нажать кнопку/тапнуть, при необходимости положить
   на зарядку на 10–20 секунд.
3. **Сканировать 60 секунд**, а не 5:

   ```bash
   python windows/miband_1a_reader.py --scan 60
   ```

   Искать имя `MI1A` / `MI BAND`; MAC в примерах — `AA:BB:CC:DD:EE:FF`.

4. **Сопряжение**:

   ```bash
   python windows/miband_1a_reader.py --mac AA:BB:CC:DD:EE:FF --pair
   ```

   В момент `FF0F <- 0x02` браслет вибрирует; **нажать на него в течение 5 секунд**.
   Если не успеть — SMP не завершится, будет `status=133` или таймаут.

5. **Авторизация**:

   ```bash
   python windows/miband_1a_reader.py --mac AA:BB:CC:DD:EE:FF --auth
   ```

   Успех — `0x05` на `FF03`. Отказ — `0x06`.

6. Только после `0x05` читать батарею/шаги/историю.

## Почему авторизация может «молчать»

- **Неверный CRC**: нужен Dallas/Maxim (0x8C), а не poly 0x07.
- **Неверный последний байт MAC** в XOR — проверь, что MAC тот, к которому
  реально подключились.
- **`feature` не 5 / `appearance` не 0** — для 1A именно эти значения.
- **Запись `UserInfo` без response** — браслет принимает только с подтверждением.
- **Нет `0x05` после SMP** — скорее всего не нажали на браслет вовремя
  или потеряли bond.
- **Удалили bond** — не надо: после сброса браслета сохранённый bond ESP32
  как раз и держит SMP. Удаление давало `reason 19`.

## Почему `char not found`

Если в логе `char ff04 not found` и т.п. — подключились не к тому устройству
или сервис ещё не обнаружен. Проверь имя/адрес и делай `SEARCH_CMPL` до
поиска характеристик; не открывай соединение повторно, пока идёт discovery.

## Автоопрос после сопряжения

ESP32-прошивка после успешного pair:

- держит bond;
- периодически ищет браслет в эфире;
- при появлении подключается, читает `FF0C` (батарея) и `FF06` (шаги);
- публикует `mks/miband/*` в MQTT;
- отдаёт историю активности, если она запрошена.

Автоопрос **не делает** браслет постоянно видимым: если телефон снова
подключился, ESP32 честно получит таймаут. Это ограничение BLE, а не баг.

## Быстрый чек-лист

- [ ] Bluetooth на телефоне выключен / Mi Fit закрыт;
- [ ] браслет разбужен кнопкой;
- [ ] скан 60 секунд, имя `MI1A`/`MI BAND`;
- [ ] pair и **тап в течение 5 секунд**;
- [ ] `UserInfo` 20 байт, response=True, CRC 0x8C XOR MAC;
- [ ] ответ `0x05`;
- [ ] только потом battery/steps/history.
