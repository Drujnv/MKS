# S-89: BLE-протокол (восстановлен 08.11.2026)

## 1. Идентификация

| Параметр | Значение |
|---|---|
| Имя в рекламе | `S-89` |
| Рекламный сервис | `0x90EA` |
| Профиль | вендорский **F1080001/2/3**, не F008/IH018 |
| Микросхема/стек | Goodix (в приложении есть `com.goodix.ble.*`) |
| Приложение | **Oximeter-H 1.4.2** (`com.vphealthy.oximeter`) |
| MAC | в примерах заменён на `AA:BB:CC:DD:EE:FF` |

S-89 рекламируется **только когда надет на палец**. Если телефон/приложение держит
соединение, датчик может не быть виден другим централям — это нормальное
поведение BLE, а не «сломанный датчик».

## 2. GATT

Актуальные UUID (то, что реально отдаёт устройство при подключении):

| Роль | UUID |
|---|---|
| service | `F1080001-0451-4000-B000-000000000000` |
| notify | `F1080002-0451-4000-B000-000000000000` |
| write | `F1080003-0451-4000-B000-000000000000` |

В декомпилированном SDK класса `com.vphealthy.oximetersdk.profile.VPProfile`
эти же UUID подписаны как `BATTERY_SERVICE_UUID` / `BATTERY_READ_UUID` /
`BATTERY_CONFIG_UUID`; имена исторические, это основной канал измерений.

В ESP-IDF 128-битные UUID в `SEARCH_RES` могут приходить в обратной
(строковой) ориентации:

```
00 00 00 00 00 00 00 B0 00 40 51 04 01 00 08 F1   # F1080001
00 00 00 00 00 00 00 B0 00 40 51 04 02 00 08 F1   # F1080002
00 00 00 00 00 00 00 B0 00 40 51 04 03 00 08 F1   # F1080003
```

Сравнивай обе ориентации; иначе сервис не найдётся и handles останутся нулевыми.

## 3. Команды

`OxiOperateAbstarct.getCmd()` в SDK возвращает массив из 20 байт:

```
[0] = 0x90
[1] = 0x02
[2] = 0x01   # start
[2] = 0x02   # stop
остальные 17 байт = 0x00
```

### Старт

```
90 02 01 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

### Стоп

```
90 02 02 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

**Важно:** команда `80 01 02` — это IH018/F008. К S-89 она не относится и
данных не даёт. Именно на ней мы потеряли время в первой версии.

## 4. Ответные кадры
Формат: 20 байт, начинается с `0x90 0x02`.

| Байт | Значение |
|---|---|
| `[0]` | `0x90` |
| `[1]` | `0x02` |
| `[2]` | `0x01` старт-ACK, `0x02` стоп-ACK, **`0x03` измерение**, `0x04` ADC/PPG |
| `[3]` | `0` палец не найден, `1` идёт измерение |
| `[4]` | SpO₂, % |
| `[5]` | пульс, уд/мин |
| `[6]` | HRV (по SDK `DetectData.hrv`) |
| `[7]` | PI × 10 (по SDK `perfusionIndex = 10.0f`, деление на 10) |
| `[8..19]` | нули/служебные; не интерпретируем |

### Пример живого кадра

```
90 02 03 01 63 45 d2 b7  00 00 00 00 00 00 00 00 00 00 00 00
│  │  │  │  │  │  │  └─ PI = 0xB7/10 = 18.3 %
│  │  │  │  │  │  └──── HRV = 0xD2 = 210
│  │  │  │  │  └─────── пульс = 0x45 = 69
│  │  │  │  └────────── SpO₂ = 0x63 = 99
│  │  │  └───────────── 1 = палец есть
│  │  └──────────────── 3 = измерение
│  └─────────────────── 2
└────────────────────── 0x90
```

Старт-ACK выглядит как `90 02 01 01 ...` — не путать с измерением.

## 5. Батарея (подтверждено живым кадром 08.11.2026)

`SettingAndGetOprate.readBatterInfo()` делает:

```
[0] = 0x90
[1] = 0x01
[2] = 0x02   # KEY_GET_BATTERY
```

То есть запрос батареи — **`90 01 02 00 ... 00`** (20 байт) в F1080003.
Ответ `getBatteryData()`:

- `[2] == 2` — тип «батарея»;
- `[3]` — `EnumAck` (1 = SUCCESS);
- `[4]` — `EnumBattery`: 1 normal, 2 charging, 3 full, 4 low; `0` — unknown;
- `[5]` — **число делений 0..4, НЕ проценты**; проценты = `raw * 25`.

Живой ответ:

```
90 01 02 01 00 04 00 00 ...
             │  │  └── 4 деления = 100 % (на экране S-89 было 100 %)
             │  └───── статус 0 (в enum не входит; считать неизвестным)
             └──────── ACK=1
```

Ошибка первой версии: я прочитал `0x04` как «4 %». На экране было 100 %;
правильно `4/4` деления.

## 6. F102 / ADC / PPG (подтверждено живым потоком)

Второй вендорский сервис: `F1020001`, notify `F1020002`, write `F1020003`.
`LightChannelOprate.openAdcNotify()` просто подписывается на F1020002;
`getAdcData()` режет кадр на **5 сэмплов по 3 байта**, начиная с `[3]`,
и каждый 24-битный семпл прогоняет через `convert_ecg_value`.

Живые кадры идут двумя типами, оба с 5×3 байтами:

```
90 02 04 01 f7 58 01 f7 90 01 f1 5a 01 e3 25 01 d6 89 00 00   # канал 4
90 02 05 03 51 50 03 55 07 03 59 11 03 5d 3b 03 60 30 00 00   # канал 5
```

`[2]=4` и `[2]=5` — два световых канала (сырые ADC). В reference client
это `--ppg`; формула `convert_ecg_value` (знаковое расширение 21 бита)
и отрисовка волны в HA ещё не сделаны.

## 7. Как проверяли

1. Взяли реальные кадры Windows BLE-клиентом (`bleak`) с собственным S-89.
2. Статически разобрали **Oximeter-H 1.4.2**: `VPProfile`, `DataOprate`,
   `OxiOperateAbstarct`, `DetectData`.
3. Сверили каждое поле с живым потоком:
   - `[4]` меняется 98–100 при нормальном дыхании;
   - `[5]` 60–70 в покое;
   - `[7]` даёт PI 1.5–2.0 после деления на 10.
4. Проверили на ESP32-C3 (R4sGate): авто-скан, подключение, notify, старт,
   разбор. Датчик отдаёт данные без приложения.

## 6. Ограничения

- **Температуры нет** — в `DetectData` S-89 только `spo2h`, `heart`, `hrv`,
  `perfusionIndex`.
- **PPG-волна** живёт на F102/ADC; в этой версии проекта не включена.
- **Батарея** отдельным кадром не проверена; не выдавай старые 87 % за заряд S-89.
- **История** измерений не читается — только live.
- **Не медицинское изделие**: не использовать для диагностики.
- Числа зависят от посадки на палец, движения и холода; PI — не «качество», а
  перфузия.

